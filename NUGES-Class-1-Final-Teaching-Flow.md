# NUGES MEDIA & ADVERTISING
## Class 1 Final Teaching Flow

Purpose: provide the content specification for the learner-facing HTML note and the facilitator's 3-hour delivery.

Audience: NUGES participants in creative, production, strategy, operations, research, and client work.

Core promise: participants leave able to explain an AI system, distinguish prompt engineering from context engineering, co-build one shared NUGES organizational context engine, and start a private personal context engine.

Evidence rule: use verified public NUGES information and information explicitly authorized by participants or a NUGES representative. Label every other NUGES-specific item `[NUGES TO CONFIRM]`. Never invent services, clients, staff, results, workflows, policies, or approval owners.

Language rule: biology explains roles and information flow only. AI is not alive, conscious, emotional, biological, or equivalent to a human being.

No em dashes are used in the learner-facing copy.

## 1. Corrected content architecture for the HTML note

### A. Cover and orientation

Show:

- NUGES MEDIA & ADVERTISING
- Class 1: AI Foundations and Context Engineering
- A one-line promise: "Build the system around the model."
- Duration: 3 hours
- Progress indicator with five class sections
- Light/dark mode toggle with localStorage persistence

Facilitator cue: state that this is a working session, not a lecture. Participants will test understanding, co-build a shared system, and begin a personal system.

### B. Architecture first: the biology-to-AI reveal

Place a large SVG diagram before the glossary. The diagram starts with a labelled biological systems illustration and reveals the AI system in layers:

1. brain, mapped to model
2. senses and incoming signals, mapped to inputs and context
3. bloodstream, mapped to information and resource distribution
4. memory store, mapped to retained information
5. nervous system, mapped to APIs and communication
6. body and environment, mapped to the harness and workspace
7. hands, mapped to tools
8. feedback and adaptation arrows, mapped to evaluation and revision
9. skin and immune boundary, mapped to guardrails
10. small callouts for prompt, MCP, and WebSockets

The first caption must say: "This is a systems analogy. It explains roles and flow. It does not make AI biological or alive."

Learner action: click or scroll through each layer and say what the layer contributes to a useful NUGES task.

### C. Section 1, AI Foundations through biology illustrations

Use visual concept cards, not long prose. Each card contains:

- short biology scene
- AI mapping
- plain-language explanation
- analogy boundary
- optional NUGES example

Use the specifications in section 3 of this brief.

Include a persistent checklist:

- I can explain what AI is and is not.
- I can distinguish a model from a full AI system.
- I can locate prompt, context, memory, and harness.
- I can explain API, MCP, and WebSockets operationally.
- I can identify tools, feedback loops, and guardrails.

### D. Section 2, Foundational concept check

Title: "Can you diagnose the system?"

This is a knowledge check, not a context-building exercise. Use short individual and pair cards. Some cards ask learners to paste a prompt into their own LLM. Do not ask them to create an organizational context template yet.

Include a reveal button for facilitator answer keys. The learner-facing page should show the task first and keep the answer in a collapsible checkpoint panel.

### E. Section 3, Prompt engineering versus context engineering

Start with a two-column visual:

- Prompt: the message sent for the immediate task
- Context: the surrounding world assembled around the task

Then show the same NUGES task in three passes:

1. bare prompt
2. improved prompt with a short, verified NUGES context block
3. short task prompt using a shared context engine in the harness

Add a warning card:

"Adding prompt text or supplying context changes what the system sees for this work. It does not update the model's weights. Weight updates require a separate training or fine-tuning process."

### F. Section 4, Live collaborative build: shared NUGES context engine

This section must feel like a live room activity. Do not provide a large blank template.

The HTML should show a stack of short prompt cards. The facilitator runs one card, the room supplies or challenges the content, and the harness or LLM stores the accepted result in the shared context engine.

Show four evidence labels throughout:

- Verified public
- Authorized internal
- Proposed
- `[NUGES TO CONFIRM]`

Show a visible stop rule: "Unknown is a valid result. Guessing is not."

The live build must produce a working context engine inside the approved harness or LLM, not a long document passed around afterward.

### G. Section 5, Assignment: personal context engine

Explain the separation:

- shared NUGES context holds organizational truth, rules, boundaries, and approved examples
- personal context holds the participant's role, responsibilities, goals, preferences, recurring work, quality standards, and review habits

Show short prompt cards, not a giant template. Each learner runs the cards in their own harness and LLM, adapts the questions, and saves the result privately.

End with a deliverable checklist and one short handoff line:

"Bring the personal context engine and one test result to the next class."

Do not add a Class 2 build section.

### H. HTML interaction requirements

- SVG architecture diagram with progressive layer reveal
- visual comparison cards for model, prompt, context, memory, and harness
- terminal-window styling for prompt cards
- facilitator cue and learner action callouts
- collapsible answer keys
- localStorage-backed checklist
- light/dark toggle with persistence
- no external network dependency required for the note
- no fictional NUGES facts in examples

## 3. Biology illustration specifications for each concept

Use one consistent side-view body silhouette or cutaway. Reveal layers in order. Use biology as a visual language for roles and flow only. Do not draw the AI as a person, give it facial expressions, or describe it as wanting, feeling, knowing, or deciding independently.

### 1. What AI is and is not

- Biology scene: a labelled systems exhibit with organs, signals, pipes, tools, and an outer boundary. A caption says "parts working together," not "a living AI."
- AI mapping: a human-built system made from a model, instructions, information, interfaces, tools, permissions, feedback, and controls.
- Plain explanation: AI is software that transforms inputs into outputs using learned patterns and surrounding system design.
- Boundary: the analogy does not imply life, consciousness, emotion, agency, or human equivalence.
- NUGES example: a system can help draft a content idea when the model, approved NUGES context, prompt, and review rule are assembled.

### 2. Model, shown as the brain

- Biology scene: a brain in a cutaway, with an arrow showing pattern processing.
- AI mapping: model.
- Plain explanation: the model generates or transforms patterns. It is one component, not the complete AI system, and it does not automatically know NUGES.
- Boundary: a model is not a human brain and does not possess human understanding or experience.
- NUGES example: a language model can draft campaign language but cannot know an unprovided NUGES service boundary.

### 3. Inputs and context, shown as senses and a nearby scene

- Biology scene: eyes, ears, and skin receive signals from labelled objects nearby: a brief, source page, audience description, and constraints.
- AI mapping: inputs and task context.
- Plain explanation: context is relevant information supplied around the immediate task, such as facts, examples, current state, audience, objective, and constraints.
- Boundary: senses can misread signals, and context can be incomplete, stale, irrelevant, or too large. Context is not automatically true.
- NUGES example: the approved public NUGES facts and a current task brief can be supplied for a positioning draft.

### 4. Harness, shown as the body and operating environment

- Biology scene: the whole body around the brain, including organs, boundaries, and the environment it operates in.
- AI mapping: harness, workspace, workflow, state, permissions, context assembly, tools, and output handling.
- Plain explanation: the harness wraps the model and controls what it receives, what it can access, what tools it can call, and how results are reviewed or saved.
- Boundary: a body is biological and self-regulating in ways a harness is not. A harness only does what its software and permissions define.
- NUGES example: an approved workspace may assemble a brief and source pages, then keep a draft from being published automatically.

### 5. Prompt, shown as an instruction card entering the system

- Biology scene: a labelled instruction card is delivered to a system operator, without drawing a talking brain.
- AI mapping: the immediate request and instructions for this task.
- Plain explanation: a prompt says what to do now and can specify output format, audience, constraints, and quality checks.
- Boundary: a prompt cannot supply facts that are missing and cannot grant permissions that the harness does not provide.
- NUGES example: "Draft three public-facing positioning ideas using only the supplied verified facts."

### 6. Context, shown as the surrounding world and bloodstream inputs

- Biology scene: a close-up of the body receiving a current scene, while labelled blood vessels distribute oxygen, nutrients, and signals to the right organs.
- AI mapping: relevant information assembled and distributed to the model for the current task.
- Plain explanation: context gives the model the facts, examples, objectives, current state, and constraints it needs without relying on repeated explanation in every prompt.
- Boundary: tokens are not nutrients, and context does not become permanent memory just because it was supplied once.
- NUGES example: a task brief, approved audience guidance, source links, and a review checklist travel together for a campaign-brief draft.

### 7. Memory, shown as a labelled long-term record store

- Biology scene: a separate archive connected to the body, with dated cards entering and stale cards being removed.
- AI mapping: intentionally retained information available across future tasks.
- Plain explanation: memory stores approved, useful, and reviewable facts, preferences, decisions, or history. It should have an owner and a refresh or expiry rule.
- Boundary: memory can be wrong or stale. It is not perfect recall, and it must not retain private information merely because it could personalize an answer.
- NUGES example: an approved glossary or decision record may be retained, while an unverified claim stays `[NUGES TO CONFIRM]`.

### 8. API, shown as a nervous-system communication pathway

- Biology scene: labelled nerve pathways carry a request from one organ to another and return a result.
- AI mapping: a programmatic interface through which one software system requests data or an action from another.
- Plain explanation: an API is an agreed way for software systems to communicate, usually with defined inputs, outputs, and permissions.
- Boundary: an API is an interface, not a source of truth, reasoning ability, or automatic authorization.
- NUGES example: an approved workflow might request a current brief from a connected system through an API.

### 9. MCP, shown as a labelled junction board

- Biology scene: a connector junction with labelled ports that lets a system discover which external capabilities are available.
- AI mapping: Model Context Protocol, an AI-oriented connection pattern for discovering and using approved tools and context providers.
- Plain explanation: MCP can give an AI workspace a structured way to discover available tools or context sources and use them under configured permissions.
- Boundary: MCP does not train the model, guarantee accuracy, or make an unsafe tool safe. The connected server and permissions still matter.
- NUGES example: an approved NUGES workspace could connect to a knowledge source or search tool through an MCP server if authorized.

### 10. WebSockets, shown as a live two-way line

- Biology scene: a continuous two-way signal line between two labelled stations, with messages moving in both directions over time.
- AI mapping: a persistent communication channel for near-real-time messages.
- Plain explanation: WebSockets keep a connection open so a system can send and receive updates without creating a new connection for every message.
- Boundary: WebSockets describe transport, not intelligence, truth, or permissions. A live channel can still carry bad or unauthorized information.
- NUGES example: an approved collaboration surface could stream task status to a dashboard. It is not needed for an ordinary one-off draft.

### 11. Tools, shown as hands and external organs

- Biology scene: hands pick up a calculator, a search lens, and a file folder, each with a visible permission label.
- AI mapping: callable capabilities that retrieve information or perform an action.
- Plain explanation: tools extend what the system can do beyond generating text, but each tool needs scope, permissions, and review.
- Boundary: a tool result can be incomplete or wrong, and access to a tool is not approval to take an external action.
- NUGES example: search, calculation, document lookup, or preparing a draft. Publishing or sending remains behind a human gate.

### 12. Feedback loops and neuroplasticity, shown as test, diagnosis, and revision

- Biology scene: a signal is tested, a mismatch is observed, and a pathway is adjusted. Label the loop "result, evaluate, diagnose, revise."
- AI mapping: feedback loop for improving the prompt, context, harness, tool use, or rule. Model training is a separate process.
- Plain explanation: reliable work improves when the output is checked against criteria, the failure layer is identified, and one change is tested.
- Boundary: feedback during a task does not update model weights. A system may update context or rules, while weight changes require controlled training or fine-tuning.
- NUGES example: compare a draft with verified NUGES facts, discover an unsupported claim, then revise the context or guardrail.

### 13. Guardrails, shown as skin and an immune boundary

- Biology scene: a labelled outer boundary blocks a harmful substance and routes an uncertain signal to review.
- AI mapping: technical and human controls that limit unsafe, unauthorized, private, misleading, or irreversible behavior.
- Plain explanation: guardrails define what the system may see, retain, say, or do, and when a human must review or approve.
- Boundary: a boundary can be incomplete or misconfigured. Guardrails reduce risk but do not make outputs automatically correct.
- NUGES example: no unsupported NUGES claims, no restricted client material in an unapproved tool, and human approval before external use.

### Visual design constraints

- Use neutral colours for biology and a contrasting accent for AI labels.
- Keep the same silhouette while layers are revealed, so learners see one system becoming more complete.
- Use arrows to show information flow, not eyes or facial expressions to imply consciousness.
- Label "model" inside the brain and "full AI system" around the entire diagram.
- Show prompt as a message, context as the surrounding information field, memory as a separate retained store, and tools outside the model.
- Add a small warning under the illustration: "Analogy for roles and flow only."

## 4. Concept-check exercise with answer keys

Facilitator instruction: learners answer first. Reveal the checkpoint only after an individual or pair has committed to an answer.

### Exercise 1, build a new analogy

Prompt to paste into an LLM or answer verbally:

"Explain MCP using a biology analogy that is different from the one in class. Map the roles, give one NUGES media example, and state one limitation. Do not describe AI as alive or conscious."

Checkpoint: the analogy must preserve these roles: MCP is a connection pattern for discovering and using approved tools or context providers; it is not the model, not training, and not a guarantee of accuracy or permission.

### Exercise 2, diagnose the missing component

For each scenario, name the primary missing or weak component and explain why.

A. "The model produces generic campaign ideas for NUGES even though the request says 'make it sound like NUGES'."

B. "The assistant can read an approved brief but cannot retrieve the current version from the connected workspace."

C. "The assistant drafts a strong public post and publishes it immediately."

D. "The assistant uses last year's approved voice rule even though it has been replaced."

Answer key:

- A: context is missing or too vague. A prompt naming NUGES is not enough to supply verified voice, audience, examples, or constraints.
- B: the retrieval tool or API connection is missing, unavailable, or not permitted. The model cannot retrieve a file merely because the user mentions it.
- C: guardrails, permissions, and human approval are missing or bypassed. Drafting permission is not publishing permission.
- D: memory is stale or the review and feedback loop failed. Update or retire the retained rule and record the source and review date.

Facilitator note: some scenarios can have more than one contributing layer. Accept the primary diagnosis if the explanation identifies the missing control or information flow.

### Exercise 3, match the systems

Match each biology component to the AI component:

1. brain
2. senses
3. long-term record store
4. nervous-system pathway
5. hands
6. outer protective boundary
7. test and adjustment cycle
8. whole body and environment

Options: model, inputs and context, memory, API, tools, guardrails, feedback loop, harness.

Answer key: 1 model, 2 inputs and context, 3 memory, 4 API, 5 tools, 6 guardrails, 7 feedback loop, 8 harness.

### Exercise 4, model versus full system

Answer in two sentences:

"Why is a language model not the whole NUGES AI system? Name four things around the model that determine whether the result is useful and safe."

Checkpoint: a strong answer says the model generates or transforms patterns, while the full system also supplies prompt, context, memory, harness, tools, interfaces, permissions, feedback, and guardrails. Any four surrounding layers are acceptable if explained accurately.

### Exercise 5, context versus memory

Classify each item as current task context, retained memory, both only if deliberately stored, or neither.

- the approved brief for today's campaign-brief exercise
- a dated NUGES glossary approved for repeated use
- a participant's private medical detail
- a current audience constraint supplied for today's task
- an unsupported claim copied from a generated answer

Answer key:

- today's approved brief: current task context
- dated approved glossary: retained memory, and it may also be supplied as context when relevant
- private medical detail: neither, unless a separate explicit and approved need exists, which is outside this exercise
- current audience constraint: current task context, and only retained as memory if intentionally approved and still useful
- unsupported generated claim: neither. Generated text is not a source.

Teaching line: context is what the system needs now. Memory is what the system is deliberately allowed to retain for later.

### Exercise 6, API, MCP, and WebSockets in operational language

Complete these three sentences without using the words "magic" or "intelligence":

- "An API is ..."
- "MCP is ..."
- "WebSockets are ..."

Checkpoint answer:

- An API is a defined programmatic interface for one system to request data or an action from another.
- MCP is an AI-oriented connection pattern for discovering and using approved tools and context providers.
- WebSockets are a persistent two-way transport for near-real-time messages.

Ask: "Which of these, by itself, proves that a result is accurate or authorized?" Answer: none.

### Exercise 7, locate the approval gate

For each action, say draft allowed, human approval required, or prohibited until an approved process exists:

- draft three internal content ideas using public facts
- retrieve a public NUGES web page
- send a client email
- publish an advert
- include a confidential client brief in an unapproved AI tool
- prepare a campaign brief for human review

Answer key:

- draft internal content ideas: draft allowed, subject to the agreed review rules
- retrieve a public page: allowed when the tool and use are approved
- send a client email: human approval required
- publish an advert: human approval required
- confidential brief in an unapproved tool: prohibited
- prepare a campaign brief for human review: draft allowed, with the data boundary applied

Final concept-check gate: each learner can accurately explain at least five cards, and the room resolves the API, MCP, WebSockets, context, memory, and approval distinctions without facilitator rescue.

## 5. Prompt engineering versus context engineering

### The core distinction

Prompt engineering improves the immediate message sent to the model. It can clarify the task, audience, format, constraints, examples, and success criteria.

Context engineering designs the information environment around the model. It decides which sources, facts, examples, current state, rules, permissions, memory, tools, and review steps are assembled for the task.

Prompting is still useful. A precise task request helps the system act on the available information. But prompting cannot compensate for missing organizational knowledge. If NUGES's approved services, voice, audience, or decision rules are absent, adding adjectives to the prompt does not make them appear.

Context reduces repetition. The participant should not have to re-explain the same verified facts, preferences, standards, and constraints every time. The context engine can assemble them when relevant, with evidence and permissions attached.

Neither ordinary prompting nor supplying context updates model weights. They change the information available to that task. Weight updates require a separate, controlled training or fine-tuning process.

### Visual instruction

Draw a message card entering a model on the left and a complete surrounding workspace on the right.

Left: "Prompt: do this now."

Right: "Context: what the system knows for this task, what it may access, what good looks like, what it must not do, and who reviews the result."

A small footer says: "More words in the message is not the same as a better information environment."

### NUGES demonstration, pass 1: bare prompt

Paste exactly:

"Give me five social media campaign ideas for NUGES."

Facilitator asks learners to inspect the output for generic language, unsupported services, invented audience assumptions, invented results, missing review criteria, and no approval boundary.

### NUGES demonstration, pass 2: short improved prompt with verified context

Paste exactly:

"You are helping with a low-risk draft for NUGES Media. Use only these verified public descriptions: NUGES presents itself as a communications and media agency built for the next generation of brands. Its public 'Who We Are' page describes work with startups to industry leaders across diverse sectors and says it helps grow and nurture brands, enhance visibility, engage audiences, tell stories, and drive measurable results. Draft three content ideas for prospective clients. For each, include audience, purpose, hook, and a clear reason it is grounded in the supplied facts. Do not invent services, clients, case-study results, prices, staff, or performance claims. Mark any missing NUGES-specific fact as [NUGES TO CONFIRM]. Draft only."

Sources for the supplied facts:

- https://nugesmedia.com/
- https://nugesmedia.com/meet-nugesmedia/

Facilitator asks: "What improved because facts, boundaries, format, and evidence handling were supplied?"

### NUGES demonstration, pass 3: context engine around the model

In the approved harness or LLM, save the public facts and the agreed rules as shared context. Then use the shorter task prompt:

"Using the shared NUGES organizational context and the approved public sources, draft three low-risk content ideas for prospective clients. Show the audience, purpose, hook, source basis, and [NUGES TO CONFIRM] gaps. Draft only. Do not publish or invent organizational facts."

Facilitator asks learners to compare pass 2 and pass 3. The point is not that the third output must always be better. The point is that the surrounding system can assemble reusable context, rules, source status, and permissions without pasting the whole explanation into every request.

### Demo checkpoint

Learners must be able to say:

- pass 1 improved mainly by clarifying the prompt
- pass 2 improved because verified context and constraints were supplied in the task
- pass 3 demonstrates a context engine because the harness assembles reusable organizational information and rules around a short request
- none of the passes changed the model's weights

## 6. Collaborative NUGES context-engine prompts

Facilitator setup before running the cards:

Use the approved private harness or LLM. Do not use confidential client material, credentials, personal identity numbers, health information, or restricted files. Ask an authorized NUGES representative to identify what may be used. If no authorized representative or source is available, use public facts only and label internal fields `[NUGES TO CONFIRM]`.

Run this anchor prompt once:

"We are co-building a shared NUGES organizational context engine. Use verified public sources and statements explicitly authorized by a NUGES representative or approved internal material. Label every item Verified public, Authorized internal, Proposed, or [NUGES TO CONFIRM]. Never infer services, clients, results, policies, roles, workflows, permissions, or approval owners. For each accepted item capture its source, owner, sensitivity, permission, review date, and unresolved question. Ask the room when evidence or authority is unclear."

For every card, the facilitator pauses after the LLM response. The room contributes, challenges, accepts, rejects, or labels the candidate. Only the accepted, labelled result is stored in the shared engine.

### Card 1, choose the real low-risk task

"Ask the room to choose one real, low-risk NUGES task for today's test. Candidate types are a content idea, a campaign brief structure, or copy from an approved and sanitized brief. Do not choose publishing, sending, spending, changing records, making commitments, or using confidential data. Record the chosen task, audience, objective, allowed data, prohibited data, output format, reviewer, approval gate, and definition of done. Mark unknown fields [NUGES TO CONFIRM]."

Facilitator checkpoint: the room names the task and risk boundary before any content is generated.

### Card 2, who NUGES is

"Using only the evidence available, describe who NUGES is in a neutral fact card. Separate Verified public, Authorized internal, Proposed, and [NUGES TO CONFIRM]. Do not turn the card into marketing copy. Ask the room which description is accurate and which needs confirmation."

### Card 3, what NUGES does

"List what NUGES does, with each item tied to a source or authorized contributor. State the boundary of each service or capability. If a service, package, delivery stage, or capability is not verified, write [NUGES TO CONFIRM] rather than guessing."

### Card 4, who NUGES serves

"Describe the audiences and stakeholders NUGES serves for the selected task. Separate public evidence from participant knowledge. Ask what audience distinctions, needs, accessibility requirements, or client-selection rules still need confirmation."

### Card 5, what outcomes NUGES creates

"List the outcomes NUGES may safely describe for the selected task. Separate broad public positioning from measurable claims that require evidence. Do not invent metrics, clients, case studies, or results. Mark unsupported outcome claims [NUGES TO CONFIRM]."

### Card 6, how NUGES wants to sound

"Ask the room for observable NUGES voice rules. Capture preferred tone, sentence habits, words to use, words to avoid, claim strength, audience sensitivity, and examples that demonstrate the rule. Label every rule Proposed unless supported by an approved NUGES source or authorized contributor."

### Card 7, what NUGES must never claim or do

"Create a proposed do-not-claim and do-not-do list for this context engine. Include unsupported performance claims, invented services or clients, confidential information, unauthorized disclosure, publication, sending, spending, record changes, and irreversible actions. Mark these as Proposed rules unless NUGES policy is explicitly authorized. Ask the room to challenge omissions."

### Card 8, common workflows where AI can help

"Ask the room to nominate up to three common NUGES workflows where AI may assist. For each, capture trigger, inputs, steps, handoffs, approved tools, output, definition of done, reviewer, and stopping point. Do not invent a workflow. Use [NUGES TO CONFIRM] for missing details."

### Card 9, examples of good NUGES work

"Collect examples that represent good NUGES work for the selected task. For each example, record what makes it good, its source, its sensitivity, and whether reuse in this context is authorized. Do not create a fictional NUGES example or treat generated text as an approved example."

### Card 10, decision rules

"Turn the room's agreed decisions into short if-then rules. Cover conflicting sources, missing facts, uncertain claims, scope changes, audience changes, and readiness for external use. Name the decision owner or write [NUGES TO CONFIRM]. Keep Proposed rules separate from current NUGES policy."

### Card 11, private, restricted, and safe information

"Classify information for this context engine as public, internal, confidential, restricted, or prohibited. For each category, state whether the AI may retrieve, draft from, retain, support an action, or must not use it. Do not ask participants to paste sensitive examples."

### Card 12, human approval

"List every action in this workflow that requires human approval. Separate drafting from sending, publishing, client commitments, regulated content, disclosure, spending, deletion, and record changes. Name the approver or write [NUGES TO CONFIRM]."

### Card 13, ownership and freshness

"Design the maintenance rule for this shared context engine. For each context area, identify an owner, review date or trigger, source of truth, and what happens when information becomes stale or conflicts. If the room has not decided, record [NUGES TO CONFIRM]."

### Card 14, assemble the working engine

"Assemble the accepted cards into a working shared NUGES organizational context engine inside this harness. Keep evidence labels, sources, owners, sensitivity, permissions, review dates, unresolved questions, and approval gates visible. Do not flatten [NUGES TO CONFIRM] into prose. Make the engine usable for the selected low-risk task."

### Card 15, run and inspect the test

"Use the selected low-risk NUGES task. Run the same task first with only a short prompt, then with the shared context engine. Compare grounding, task fit, clarity, uncertainty handling, safety, and usefulness. Identify one failure layer, change one variable, rerun once, and record one remaining limitation. Do not publish, send, spend, change records, or disclose restricted information."

Facilitator checkpoint: the shared engine is working only if the room can show what it used, what it refused to infer, what changed after feedback, and where human review remains required.

### Minimum shared-engine result

The live engine contains, at minimum:

- verified public facts and source links
- authorized internal facts, if any, kept separate from public facts
- `[NUGES TO CONFIRM]` discovery gaps
- identity, services, audiences, and supported outcomes
- voice rules and prohibited claims or actions
- at least one workflow with definition of done
- approved examples or an explicit absence of examples
- decision rules and conflict handling
- data categories and permissions
- human approval gates
- owner and review or refresh rule
- one low-risk task test and one recorded revision

This is a working engine inside the harness or LLM. It is not a finished NUGES policy document.

## 7. Personal context-engine assignment prompts

Assignment framing for learners:

"The shared NUGES engine describes the organization. Your personal engine describes how you work within it. Keep it private unless you explicitly authorize sharing. Link to shared NUGES truth instead of copying restricted information. Use [NUGES TO CONFIRM] for organizational facts you cannot verify."

Run the following short sequence in your own harness and LLM. Adapt the questions to your role. Save the resulting personal context engine privately.

### Personal card 1, role and responsibilities

"Interview me briefly about my role at NUGES and my current responsibilities. Produce a concise role card. Ask follow-up questions rather than guessing. Separate my own working information from organization-wide facts."

### Personal card 2, goals

"Help me state my current goals and time horizon. For each goal, identify the outcome, why it matters, and how I will know the work is good. Do not invent NUGES targets or metrics. Mark unknown organizational targets [NUGES TO CONFIRM]."

### Personal card 3, recurring work, audiences, and stakeholders

"Ask me about my recurring NUGES tasks, their triggers, inputs, outputs, audiences, collaborators, handoffs, and approval points. Turn one recurring task into a short workflow. Do not ask me to paste confidential material."

### Personal card 4, working preferences and outputs

"Interview me about how I prefer information, drafts, questions, options, and feedback. Record observable preferences, not personality labels. Ask me to name the output formats I use most often and the level of detail each requires."

### Personal card 5, quality standards and decision rules

"Ask me what makes a result useful, accurate, on-brand, complete, and ready for review. Turn my answers into a short quality standard and if-then decision rules. Flag any rule that actually belongs to shared NUGES policy as [NUGES TO CONFIRM] rather than presenting it as personal truth."

### Personal card 6, review checklist

"Create a review checklist for my most common task. Include factual grounding, audience fit, objective, format, clarity, NUGES context link, uncertainty labels, privacy, and human approval. Keep it short enough to use before I submit work."

### Personal card 7, privacy and shared links

"Help me separate what belongs in my private personal context from what belongs in the shared NUGES organizational context. Add links to the shared pages used today without copying restricted content. List information I must not retain or share and actions that require human approval."

### Personal card 8, assemble and test

"Assemble my personal context engine v1 from the answers above. Include my role, responsibilities, goals, recurring tasks, audiences and stakeholders, preferences, preferred outputs, quality standards, decision rules, review checklist, links to shared NUGES context, privacy boundaries, open [NUGES TO CONFIRM] items, and one low-risk test task. Ask me to correct anything that is not true before saving."

### Personal assignment success criteria

Before leaving, each participant has:

- one role statement
- current responsibilities
- at least two current goals
- one recurring workflow with inputs, output, and approval point
- named audiences and stakeholders
- at least three observable working preferences
- preferred formats for two common outputs
- at least two personal quality rules
- a short review checklist
- links to shared NUGES context, or explicit `[NUGES TO CONFIRM]` placeholders
- two privacy or permission boundaries
- one low-risk test task

Closing learner action: run the personal engine against the selected low-risk task or a comparable low-risk task, save the output and one limitation, and bring both to the next class.
